# Bopzi thumbnail generation: deeper research and investigation

Research date: 31 October 2026. Scope: Roblox experience thumbnails made in Bopzi. This combines Roblox and image-generation documentation, published evaluation research, source-code inspection, and a visual inspection of existing project screenshots. It does not include new generated comparisons or measured Roblox performance. The previous 31 October report describes the pre-fix implementation; random automatic inspiration and rigid default composition have since been changed.

## What the evidence supports

1. **Truthful, legible game promise.** Roblox says imagery should make the experience clear and accurately reflect the game; misleading or non-unique metadata can limit discovery. Prefer one clearly staged gameplay moment with recognizable game-specific subjects to generic drama. This is an application of Roblox guidance, not a formula guaranteed to increase clicks. Sources: https://create.roblox.com/docs/production/publishing/thumbnails and https://create.roblox.com/docs/discovery.
2. **Judge at the actual destination.** Roblox recommends 16:9, ideally 1920×1080, and notes that bottom metadata can cover content. Bopzi's Roblox preview is already useful for checking whether pose, action, object silhouette and any words survive reduction. Do not treat 320px or a fixed safe-area percentage as an official universal device size.
3. **Actual game assets are a strong grounding option.** Studio freecam can capture an intentional viewpoint; the existing Bopzi screenshot flow offers local polish, AI restyle, and area edit. An in-game screenshot can preserve recognizable assets and relationships, though it still needs intentional camera, lighting and staging; it is not automatically an effective thumbnail. Roblox freecam: https://create.roblox.com/docs/production/publishing/thumbnails.
4. **Aesthetic quality, fidelity and composition are separate.** A nice image can have the wrong avatar, miss the requested action or break a tool. MMIG-Bench separates identity, prompt alignment and preference; OpenAI's image-evals guide recommends hard correctness gates and targeted human comparison. Neither research result measures Bopzi itself. https://papers.nips.cc/paper_files/paper/2025/hash/d3f8714b9f9727b43d64019f2f4043d2-Abstract-Datasets_and_Benchmarks_Track.html ; https://developers.openai.com/cookbook/examples/multimodal/image_evals.
5. **Style matching and copying are competing risks.** Clearly label reference image roles and test them on representative assets. OpenAI's image prompt guidance recommends targeted edits, explicit preservation and role assignment: https://developers.openai.com/api/docs/guides/image-prompting and https://openai.com/academy/image-generation/. The high-input-fidelity cookbook describes behavior of that specific API feature; it does not establish that Bopzi's separate Codex backend supports the same parameter or ordering behavior: https://developers.openai.com/cookbook/examples/generate_images_with_high_input_fidelity.
6. **Performance has to be measured on Roblox.** Home personalization uses 2–5 active thumbnails and qualified play-through rate; Roblox's reported +8.5% average is for the personalization system, not a promise for an individual image. One-at-a-time generation remains the user's preference. https://create.roblox.com/docs/production/publishing/thumbnails.

## Bopzi pipeline and new findings

- **Post-processing is mandatory for new generations.** `src/studio/Composer.tsx` sends each new image through `finish()` after conversion to 1920×1080. `src/studio/finish.ts` applies 0.45 sharpening, a 0.38 contrast curve, 1.08 saturation, up to 0.16 vignette and ±4.5 levels of grain. These are global fixed settings regardless of genre or user preference. The comment asserts this removes an AI look, but no comparative evidence was found. It may enhance some images while crushing dark scenes, adding halos or making clean art noisy. Test unprocessed versus processed using the exact same returned image (no extra generations), at full and preview sizes. A reversible optional finishing control is a candidate if users prefer different results.
- **Edits have a different finish path.** The `run()` path for refinements converts the returned image but does not call `finish()`, while initial generation does. A refined image may shift in contrast or grain independently of the requested edit. Compare source and edit before deciding whether to remove the finish or match it consistently.
- **Real resolution differs from export resolution.** `helper/codex-core.mjs` requests 1536×864, `quality: high`, then `toThumbnail` scales to 1920×1080. The export has the right dimensions, but interpolation does not add native visual detail; the 25% linear enlargement is not proof of poor output. If the response's aspect ratio differs, the centered cover crop can cut edges. Record actual input/output dimensions and preview the crop; only investigate different sizes if supported by the actual backend.
- **Reference representation is a real tradeoff.** `server.ts` shrinks/blurs the style image, sends a randomized 48px tile swatch, and supplies the sharp original only for a separate reading step unless hands are explicitly preserved. The checked-in `docs/redesign/style-reference-before-after.png` visibly demonstrates strong loss of fine shapes under the blur; `style.ts` additionally rearranges tiles and uses random shuffling. This shows information loss, not that the final images are worse. Test raw-reference, current transformed-reference, and text-description-only conditions for style fidelity, unintended copying, and consistency. The sharp-reference treatment may copy objects; score that separately.
- **Preparation adds multiple interpretation steps.** `codex-core.mjs` resolves each `{{...}}` question in its own call before image generation. Scene rewriting occurs even with no references; style inspiration adds style/recipe questions. These extra steps may reinterpret details or add latency. Preserve the original brief and capture the final substituted prompt in a local, opt-in diagnostic record; avoid logging private images by default. Compare rewritten and direct briefs with identical test cases before removing the rewrite.
- **Style presets still impose strong defaults.** `prompt.ts` has detailed render, material and lighting prescriptions; the selected 3D render preset includes a low, wide-angle camera, strong side lighting, coloured rim light, dark shadows and a two-colour scheme. These may override the desired look or scene despite the new flexible default composition. Test with a few genre-specific prompts and make camera/lighting conditional or less prescriptive only if comparisons support it.
- **Style and layout controls are not identical.** The explicit inspiration path can still borrow layout, and its transformed image can influence colours even where a non-match style is chosen. Evaluate user-selected inspiration with both layout settings and every style option; check whether each control has the effect its label promises.
- **Editing is locally bounded but can drift inside the region.** Existing marked-area editing combines the generated result with original pixels outside the selected region. Test boundary artifacts, hand/object identity and edits inside the marked rectangle, not only outside preservation.
- **Image text is not the same as editable text.** The thumbnail prompt permits a supplied title to be rendered into the image; Bopzi also has editable text layers. Test short literal text for spelling at full and preview sizes. Editable lettering offers deterministic edits but should remain optional when integrated lettering is artistically useful.
- **Existing screenshot reviewed.** `docs/redesign/reference-mining-result.png` shows a large avatar, drill and smiling object with overlaid numeric callouts; the central action reads at the captured size, but its interface overlays obscure part of the image. It is a historical UI screenshot, not evidence of current generator quality or user preference. The chosen reference and original brief were not available from this screenshot, so fidelity cannot be judged.

## Practical visual test set

Collect user-provided disliked output, ideal references and matching briefs when available. Until then use neutral fixtures and label them synthetic:

1. Obby: avatar jumps toward a checkpoint above lava; verify direction, checkpoint and scale.
2. Simulator: named character mines a named crystal with one intact tool; verify identity, grip and actual object.
3. Horror: avatar hides from a specified threat in a dark corridor; verify low-light readability without making it cheerful.
4. First person: two visible referenced hands interact with one target outdoors; exclude water; verify viewpoint and exclusions.
5. Screenshot-grounded: preserve recognizable geometry, objects and camera while adjusting light.
6. Style-only: same brief with two distinct visual inspirations, preserving game-specific subjects, without copying unrelated characters or logos.
7. Text: exact short title, separately compare image-rendered and editable text.
8. Editing: one object change with everything outside a marked area preserved.

For each, fix input assets and instructions, preserve the actual prompt and dimensions, and create blinded randomized A/B comparisons. Multiple runs per condition are required because generation is stochastic; keep a holdout group of briefs to avoid tuning only to the fixtures. Rate separately: (a) mandatory objects, action and exclusions, (b) identity, (c) action and spatial plausibility, (d) small-size readability, (e) style match, (f) original-game fidelity, (g) defects, (h) personal preference. A hard failure should not be cancelled by a pretty score. Include neither-image-good and tie options. Record latency and failure rate. The user can create variants intentionally one at a time; the evaluation is a developer experiment, not a return to four outputs per click.

## Recommended investigation order

1. Compare original and automatically finished pixels from the same generation: inexpensive and isolates processing.
2. Save exact final prompt and diagnose whether rewrite or presets change the user's intent.
3. Evaluate transformed versus clearer reference approaches while checking copying and identity separately.
4. Review a representative real set blind at Roblox preview size and full size with the user's taste as the main aesthetic signal.
5. Only after these establish a failure, implement the smallest relevant fix and repeat against held-out cases. Real Roblox personalization data is the later test of player behavior, not a substitute for checking image fidelity.
